ยกระบบเว็บอายุ 10 ปีมาเป็นปัจจุบัน โดยไม่ต้องหยุดธุรกิจ

ชื่อหัวข้อที่ใช้กันในวงการคือ Application Modernization หรือ Legacy Migration — และวิธีที่ได้ผลที่สุดมีชื่อเฉพาะว่า Strangler Fig: สร้างระบบใหม่ขึ้นข้างๆ ระบบเดิม ย้ายงานไปทีละส่วน จนระบบเดิมไม่มีอะไรเหลือให้ทำแล้วค่อยปิด หน้านี้ครอบคลุมทั้ง backend (.NET Framework → .NET 10), frontend, และการแยกฐานข้อมูลใหม่ออกจากของเดิม

คำถามแนวทาง
ย้ายอะไรก่อนmodule ที่ คุณค่าสูง + dependency น้อย และมีคนใช้พอที่จะพิสูจน์ได้ว่าทำงาน — ไม่ใช่ตัวที่ง่ายที่สุด (พิสูจน์อะไรไม่ได้) และไม่ใช่ตัวที่ยากที่สุด

ของหน้าตาต่างกันใส่ layout/header เดียวกันทั้งสองฝั่งช่วงเปลี่ยนผ่าน ผู้ใช้ไม่ควรรู้ว่าข้ามระบบ
ถอยกลับแก้กฎที่ proxy กลับไปฝั่งเดิม — ย้อนได้ในไม่กี่นาทีตราบใดที่ข้อมูลยัง sync อยู่ (หัวข้อ 6, 7)
ระบบเดิมยังต้องแก้ห้ามเพิ่มฟีเจอร์ใหม่ใน module ที่กำลังย้าย (feature freeze เฉพาะ module) ฟีเจอร์ใหม่ไปลงฝั่งใหม่เท่านั้น

04Backend — .NET Framework 4.x → .NET 10

ภาษา C# และ logic ส่วนใหญ่ยกมาได้ สิ่งที่เปลี่ยนจริงคือชั้นที่ผูกกับ IIS / System.Web — ตารางนี้บอกว่าของเดิมแต่ละตัวไปอยู่ที่ไหน

ของเดิม (.NET Framework)ปลายทาง (.NET 10)ความยาก / หมายเหตุ

WCF servicegRPC หรือ REST · หรือ CoreWCF ถ้า client เปลี่ยนไม่ได้ขึ้นกับว่าใครเรียก — client ภายนอกที่ใช้ SOAP อยู่ ใช้ CoreWCF ต่อไปก่อน

ลำดับการ upgrade โค้ดที่ยกมาได้

1. แยก class libraryดึง logic ที่ไม่แตะ System.Web ออกเป็น project แยก แล้ว multi-target net48;net10.0 — ใช้ร่วมกันทั้งสองระบบได้ระหว่างเปลี่ยนผ่าน
2. SDK-style projectแปลง .csproj แบบเก่าเป็น SDK-style, packages.config → PackageReference
3. ไล่ dependencyNuGet ทุกตัวต้องมีเวอร์ชันที่รองรับ .NET 10 ตัวที่ไม่มี → หาแทนก่อน
4. web project ใหม่สร้าง ASP.NET Core project ใหม่ (ไม่แปลงของเดิม) แล้ว reference library จากข้อ 1
5. โครงใหม่จัดตาม Clean / Vertical Slice (ดูหน้า layer-architecture) — ไม่ยกความยุ่งเดิมมาทั้งก้อน

  <PropertyGroup>
    <TargetFrameworks>net48;net10.0</TargetFrameworks>

05Frontend — จาก WebForms / jQuery สู่ UI ปัจจุบัน

การย้ายที่ใหญ่ที่สุดไม่ใช่เปลี่ยน framework แต่คือเปลี่ยนจาก "server สร้าง HTML พร้อมข้อมูล" เป็น "UI เรียก API" — ต้องมี API ก่อน frontend ใหม่ถึงจะเกิดได้

ทางเหมาะเมื่อ
Razor Pages / MVC ใหม่ (server-rendered)ทีมเป็น .NET ล้วน, หน้าเป็นฟอร์ม/ตารางเป็นหลัก, ไม่ต้องการ interactivity มาก — ย้ายเร็วที่สุด เพิ่ม htmx เมื่อต้องการ interactive บางส่วน
Blazor (Server / WebAssembly / Auto)ทีม .NET อยาก interactive โดยไม่เขียน JS, แชร์ model C# ระหว่าง UI กับ API — ระวังขนาดดาวน์โหลดของ WASM และ connection ของ Server
SPA: React / Vue / Angular + APIUI ซับซ้อน, มีทีม frontend แยก, จะมี mobile app ใช้ API เดียวกัน (ดูหน้า react-vue-angular)
ฝังทีละส่วน (islands)ยังย้ายทั้งหน้าไม่ได้ — ฝัง component ของ Vue/React ลงในหน้าเดิม (<div id="order-grid">) เพื่อทดลองและค่อยๆ ขยาย
ประเด็นแนวทาง
API ก่อน UIออกแบบ API ใหม่ตาม use case (/api/v2/orders) ไม่ใช่ห่อ stored proc เดิมเป็น endpoint ทีละตัว — มี OpenAPI spec ให้ frontend generate client
BFF (Backend for Frontend)ถ้า UI ต้องรวมข้อมูลจากทั้งระบบเก่าและใหม่ ให้ BFF รวมให้ UI เห็น API เดียว — UI ไม่ต้องรู้ว่าข้อมูลอยู่ฝั่งไหน
Design systemสร้างชุด component กลาง (ปุ่ม, ฟอร์ม, ตาราง) ก่อนหน้าแรก — ทุกหน้าที่ย้ายมาหน้าตาเหมือนกันทันที (ดูหน้า ux-ui-controls)
URL เดิมรักษา URL ที่ผู้ใช้ bookmark / ระบบอื่นลิงก์เข้ามา หรือทำ redirect 301 ทุกตัว
เบราว์เซอร์ / อุปกรณ์ระบบ 10 ปีมักรองรับ IE — ตกลงกับผู้ใช้ให้ชัดว่าเลิกรองรับ และเพิ่ม responsive สำหรับมือถือไปพร้อมกัน

06แยกฐานข้อมูลใหม่ออกจากของเดิม

ส่วนที่ยากที่สุด เพราะโค้ดย้ายทีละ module ได้ แต่ข้อมูลเป็นก้อนเดียวที่ทุก module แชร์ ระหว่างเปลี่ยนผ่านต้องตอบให้ได้ว่า ใครเป็นเจ้าของข้อมูลแต่ละตาราง และ อีกฝั่งเห็นข้อมูลนั้นได้อย่างไร

ทางทำอย่างไรข้อดีข้อควรระวัง
A. ใช้ DB เดิมร่วมกันก่อนระบบใหม่ต่อ LegacyDB ตรงๆ อ่าน/เขียนตารางเดิมเร็วที่สุด ไม่มีปัญหา syncยังติดโครงเดิม — เป็นแค่จุดเริ่ม ใช้ร่วมกับ expand-contract เพื่อค่อยๆ ปรับ schema
B. DB ใหม่ + sync ด้วย CDCSQL Server Change Data Capture / Change Tracking หรือ Debezium อ่าน log ของ DB เดิมแล้วเขียนเข้า DB ใหม่ระบบเดิมไม่ต้องแก้โค้ด ข้อมูลตามมาเกือบ real-timeทิศเดียว (เดิม → ใหม่) — ต้องมีตัวแปลง schema (anti-corruption layer) ตรงกลาง
C. Outbox eventฝั่งที่เป็นเจ้าของเขียน event ลงตาราง outbox ใน transaction เดียวกับข้อมูล worker อ่านแล้วส่งให้อีกฝั่งถูกต้องแม้ระบบล่ม, ใช้ได้สองทิศต้องแก้โค้ดฝั่งที่เขียน — เหมาะเมื่อ module นั้นย้ายมาฝั่งใหม่แล้ว และต้องส่งกลับให้ระบบเดิมที่ยังอ่านอยู่
D. ETL batchjob คืนละครั้งดึงจากเดิมเข้าใหม่ง่าย เหมาะกับรายงาน / ข้อมูลอ้างอิงข้อมูลช้าไปหนึ่งรอบ ไม่เหมาะกับข้อมูลที่ใช้ทำงานสด
✕ Dual writeแอปเขียนทั้งสอง DB เองดูง่ายห้ามทำ — เขียนสำเร็จที่หนึ่งแต่ล้มอีกที่ ข้อมูลเพี้ยนเงียบๆ โดยไม่มีใครรู้

Expand → Migrate → Contract — เปลี่ยน schema โดยไม่พัง

1. Expandเพิ่มของใหม่ข้างของเดิม: คอลัมน์ customer_id คู่กับ cust_code เดิม, ตารางใหม่คู่ตารางเก่า — ระบบเดิมไม่พัง
2. Migratebackfill ข้อมูลเก่าเข้าโครงใหม่เป็น batch, ให้โค้ดเขียนทั้งสองที่ผ่าน trigger หรือ CDC, ย้ายการอ่านไปที่ใหม่ทีละจุด
3. Verifyเทียบจำนวนแถว, ผลรวม, checksum ต่อกลุ่ม ระหว่างเก่าและใหม่ ทุกวันจนตรงกันต่อเนื่อง
4. Contractเมื่อไม่มีใครอ่านของเก่าแล้ว (ตรวจจาก dm_db_index_usage_stats) ค่อยลบคอลัมน์/ตารางเก่า — ขั้นนี้ย้อนไม่ได้ ทำเป็นขั้นสุดท้ายเสมอ
 
-- ตรวจความตรงกันระหว่าง DB เดิมกับใหม่ (reconciliation) ทุกวัน
SELECT 'legacy' AS src, CAST(order_date AS date) AS d,
       COUNT(*) AS rows_, SUM(total) AS amount,
       CHECKSUM_AGG(CHECKSUM(order_no, total, status)) AS chk
FROM LegacyDB.dbo.tbl_Order
WHERE order_date >= DATEADD(day, -7, GETDATE())
GROUP BY CAST(order_date AS date)
UNION ALL
SELECT 'new', CAST(ordered_at AS date),
       COUNT(*), SUM(total),
       CHECKSUM_AGG(CHECKSUM(order_number, total, status_code))
FROM ShopDB.sales.orders
WHERE ordered_at >= DATEADD(day, -7, GETDATE())
GROUP BY CAST(ordered_at AS date)
ORDER BY d, src;
-- วันไหน rows/amount/chk ไม่ตรง → ไล่หาแถวที่ต่าง ก่อนย้าย traffic เพิ่ม
Anti-corruption layerตัวแปลงระหว่างโครงเก่า (tbl_Order.cust_code, status เป็นตัวอักษร 'A','X') กับโครงใหม่ (orders.customer_id, enum) — กันไม่ให้ชื่อและความหมายแปลกๆ ของเดิมรั่วเข้าโมเดลใหม่
ปัญหาข้อมูลเก่าencoding ไทย (TIS-620 ปน UTF-8), วันที่ พ.ศ./ค.ศ. ปน, รหัสซ้ำ, null ที่ควรมีค่า — ทำความสะอาดใน pipeline และเก็บรายการแถวที่แปลงไม่ได้ไว้ให้คนตัดสิน ไม่ทิ้งเงียบ

กฎทองของช่วงเปลี่ยนผ่าน: ข้อมูลแต่ละตารางมี เจ้าของที่เขียนได้เพียงฝั่งเดียว ณ เวลาใดเวลาหนึ่ง อีกฝั่งอ่านอย่างเดียวผ่าน sync — เมื่อ module ย้ายเสร็จ ความเป็นเจ้าของก็ย้ายตาม และทิศการ sync กลับด้าน

07Cutover และ Rollback — พิสูจน์ก่อนย้าย และถอยได้เสมอ

เทคนิคทำอะไร
Characterization testยิง input ชุดเดียวกันเข้าระบบเดิม บันทึกผลเป็น "ค่าที่ถูก" แล้วใช้ทดสอบของใหม่ — ไม่ต้องรู้ว่ากติกาคืออะไร รู้แค่ว่าผลต้องเหมือนเดิม (ดูหน้า unit-testing)
Shadow trafficproxy ส่ง request จริงไปทั้งสองฝั่ง ใช้คำตอบของระบบเดิม แต่เก็บคำตอบของใหม่ไว้เทียบ — ใช้กับ GET / read-only เท่านั้น
Parallel runสำหรับงานคำนวณ (เงินเดือน, ราคา, รายงาน) รันทั้งสองระบบคู่กัน 1–2 รอบบัญชี เทียบผลทุกบรรทัด
Canary / % rolloutส่งผู้ใช้ 5% → 25% → 100% ไปฝั่งใหม่ (ตาม user id ไม่ใช่สุ่มทุก request) ดู error rate และ latency แต่ละขั้น
Feature flagเปิด/ปิดฝั่งใหม่ต่อ module ต่อกลุ่มผู้ใช้ได้โดยไม่ deploy
Read-only freezeช่วงย้ายข้อมูลรอบสุดท้ายของ module ที่ sync ไม่ได้ — ปิดเขียนชั่วคราว (ประกาศล่วงหน้า) ดีกว่าเสี่ยงข้อมูลหาย
แผน Rollback ต้องตอบได้ก่อนย้าย
ถอยอย่างไรแก้กฎ proxy / ปิด feature flag — ทดลองถอยจริงใน staging อย่างน้อยหนึ่งครั้ง
ข้อมูลที่เขียนในฝั่งใหม่ต้องไหลกลับไประบบเดิมได้ (outbox หรือ sync ย้อน) ไม่งั้นถอยแล้วข้อมูลช่วงนั้นหาย
ใครตัดสินใจกำหนดเกณฑ์ล่วงหน้า เช่น error rate > 2% เป็นเวลา 10 นาที หรือยอดไม่ตรง reconciliation = ถอยทันที ไม่ต้องประชุม
เก็บระบบเดิมไว้นานแค่ไหนอย่างน้อยหนึ่งรอบธุรกิจเต็ม (ปิดเดือน / ปิดไตรมาส) หลัง module สุดท้ายย้าย แบบอ่านอย่างเดียว แล้วค่อย archive

08Roadmap — ภาพรวมทั้งโปรเจกต์

ระยะ 0 · 2–4 สัปดาห์

สำรวจ & ตัดสินใจ

  • inventory + log การใช้
  • 6R ต่อ module
  • เลือก target stack (.NET 10)
  • characterization test ชุดแรก
ได้: แผน + ลำดับ module
ระยะ 1 · 1–2 เดือน

วางรากฐาน

  • CI/CD + environment
  • proxy (YARP) หน้าระบบเดิม
  • auth กลาง / SSO
  • แยก library multi-target
  • observability ทั้งสองฝั่ง
ได้: ย้าย module แรกได้โดยผู้ใช้ไม่รู้ตัว
ระยะ 2 · 1–2 เดือน

Module แรก

  • API + UI ใหม่
  • DB ใหม่ + sync
  • shadow → canary → 100%
  • reconciliation ทุกวัน
ได้: พิสูจน์ทั้ง pipeline จริง
ระยะ 3 · ต่อเนื่อง

ย้ายทีละ module

  • ทำซ้ำรูปแบบระยะ 2
  • ปิด route เดิมทีละตัว
  • ย้าย job / report
  • Retire ฟีเจอร์ที่ไม่ใช้
ได้: traffic ส่วนใหญ่อยู่ฝั่งใหม่
ระยะ 4 · 1 รอบธุรกิจ

ปิดระบบเดิม

  • read-only 1 รอบปิดบัญชี
  • contract schema เก่า
  • archive DB เดิม
  • ถอด proxy rule / server
ได้: ระบบเดียว .NET 10

ระยะเวลาไม่ใช่ตัววัดความสำเร็จ: ตัววัดคือ ทุกเดือนมี module ที่ย้ายเสร็จและอยู่ใน production จริง — ถ้าผ่านไป 3 เดือนยังไม่มี module ไหนย้ายได้ แปลว่ากำลังกลายเป็น big-bang rewrite โดยไม่ตั้งใจ
