Monolith กับ Microservices
ต่างกันตรง “เส้นแบ่ง” อยู่ที่ไหน

สมมติระบบร้านค้าออนไลน์มี Order, Payment, User และ Inventory เหมือนกันทั้งสองแบบ สิ่งสำคัญไม่ใช่ว่ามี module อะไร แต่คือ module เหล่านั้นอยู่ใน process เดียวกัน หรือแยกเป็น service ที่คุยกันผ่าน network

โครงสร้างปกติ — Monolith เรียก module กันใน process เดียว ส่วน Microservices ต้องคุยข้าม process ผ่าน network จึงได้อิสระในการ deploy/scale แลกกับ distributed-system complexity

คำสั่งซื้อ 1 รายการวิ่งผ่านอะไรบ้าง

Request เดียวกันเดินทางต่างกัน และความต่างนี้อธิบายข้อดีข้อเสียแทบทั้งหมดของสองสถาปัตยกรรม

Monolith

POST /orders→OrderService→PaymentService→InventoryService→SaveChanges()

โดยทั่วไป flow ภายในระบบเรียกกันตรง ๆ และสามารถใช้ transaction เดียวได้ง่ายกว่า การ debug มักตาม stack trace และ log ชุดเดียวได้

Microservices

POST /orders→gateway→order-svc→HTTP/event→payment-svc→event→inventory-svc

แต่ละ service มี transaction ของตัวเอง ถ้าขั้นถัดไปพังหลังขั้นก่อนหน้าสำเร็จ อาจต้องชดเชยงานด้วย Saga/compensation และใช้ correlation ID + distributed tracing เพื่อตามเหตุการณ์ข้าม service

ทางสายกลาง: Modular Monolith

Monolith ไม่จำเป็นต้องหมายถึงโค้ดก้อนเดียวที่พันกันหมด เราสามารถอยู่ process เดียว แต่แบ่ง boundary ของ Orders, Payments, Users และ Inventory ให้ชัดเจนได้

Shop.OrdersContracts / Internal
Shop.PaymentsContracts / Internal
Shop.UsersContracts / Internal
Shop.InventoryContracts / Internal
ShopDB เดียว แต่แบ่ง ownership/schema และไม่อ่าน table ของ module อื่นตรง ๆ
orders.*payments.*users.*inventory.*

แนวคิดสำคัญคือเปิด contract เท่าที่จำเป็น ซ่อน implementation ภายใน module และคุยข้าม module ผ่าน interface หรือ in-process event เมื่อวันหนึ่งมีเหตุผลจริงให้แยก service boundary ที่ชัดอยู่แล้วจะช่วยให้ extraction ง่ายขึ้น

จะเลือกอะไรดี

เริ่มด้วย Monolith / Modular Monolith เมื่อ

  • ทีมยังเล็กและ release พร้อมกันได้
  • domain boundary ยังไม่นิ่ง
  • ระบบต้องการ transaction ข้ามหลายส่วนบ่อย
  • ยังไม่ต้องการแบก operational complexity ของ distributed system
  • ต้องการพัฒนา feature และ debug ให้เร็ว

พิจารณา Microservices เมื่อ

  • หลายทีมต้อง deploy อิสระและมี ownership ชัด
  • บาง domain มี load profile ต่างจากส่วนอื่นมาก
  • ต้องการ fault isolation หรือ technology/runtime เฉพาะจริง ๆ
  • service boundary มีความชัดจาก business capability
  • ทีมพร้อมรับ observability, network failure และ eventual consistency
สรุปใจความสำคัญ

Microservices ไม่ได้ดีกว่า Monolith โดยอัตโนมัติ แต่เป็นการย้ายความซับซ้อนจากการจัดการโค้ดใน process เดียว ไปเป็นความซับซ้อนของ distributed system แนวทางที่ดีคือเริ่มจาก architecture ที่ง่ายที่สุดที่ตอบโจทย์ และแยก service เมื่อมีเหตุผลด้านทีม, scaling, deployment หรือ domain boundary ที่ชัดเจนจริง ๆ
