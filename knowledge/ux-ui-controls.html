UX/UI · CONTROLS · ACCESSIBILITY

UX/UI ของ Control
ทุกปุ่มและทุกช่องคือคำตอบของคำถาม “ผู้ใช้ต้องตัดสินใจอะไร”

การเลือก dropdown, radio, toggle หรือปุ่มไม่ใช่เรื่องรสนิยม แต่ตามมาจากจำนวนตัวเลือก, เลือกได้กี่อัน, มีผลทันทีหรือรอกดบันทึก และผู้ใช้รู้ค่าอยู่แล้วหรือต้องเห็นตัวเลือกก่อน

01เลือก Control จากคำถาม ไม่ใช่จากความเคยชิน

ลองเปลี่ยน 3 เงื่อนไข แล้วดู control ที่เหมาะสมเปลี่ยนตามโจทย์

มีตัวเลือกกี่อัน
เลือกได้กี่อัน
มีผลเมื่อไร
ตัวเลือกน้อยโชว์ให้เห็นหมดด้วย radio / segmented / chips เพื่อเทียบได้ทันที
ตัวเลือกเยอะให้พิมพ์ค้นด้วย autocomplete/combobox แทนการเลื่อนรายการยาว
ผลทันทีToggle สื่อว่าเปลี่ยนแล้ว ส่วน Checkbox ในฟอร์มสื่อว่ายังต้องกดบันทึก
ผู้ใช้รู้ค่าอยู่แล้วให้พิมพ์ตรง ๆ เช่นวันเกิด มากกว่าบังคับเลื่อน date picker
Default ที่ดีถ้าคนส่วนใหญ่เลือกค่าเดียวกัน ตั้ง default เพื่อลด decision ที่ไม่จำเป็น

02Buttons — ลำดับความสำคัญ ป้าย และสถานะ

ปุ่มควรบอกได้ทันทีว่ากดแล้วเกิดอะไร และหน้าจอต้องมีทางหลักที่ชัดเจน

Primaryควรมี 1 ปุ่มต่อหน้าจอหรือฟอร์ม เป็นทางหลักที่ผู้ใช้ควรไป
Secondaryทางเลือกที่ทำได้แต่ไม่ใช่เป้าหมายหลัก
Tertiaryทางออกที่ไม่เสียข้อมูล เช่น ยกเลิกหรือข้าม
Destructiveสีแดงใช้กับสิ่งที่ย้อนกลับไม่ได้ เพื่อรักษาความหมายของสี

ป้ายที่ดี: กริยา + สิ่งที่ทำ

เลี่ยง “ตกลง / ยืนยัน / ปิด” ถ้าอ่านปุ่มอย่างเดียวแล้วยังไม่รู้ผลลัพธ์

Statesออกแบบ default, hover, focus, disabled และ loading ให้ครบ
Touch targetอย่างน้อย 44×44 px บน touch และเว้นระยะระหว่าง action
Loadingเปลี่ยน state ทันทีเมื่อกดและกัน double submit
Confirmถามก่อนเฉพาะ action ที่ย้อนกลับไม่ได้ ถ้าย้อนกลับได้ให้ทำเลยแล้วเสนอ Undo

04Forms และ Input

Form UX ที่ดีลดสิ่งที่ผู้ใช้ต้องเดาและบอกวิธีแก้เมื่อเกิดข้อผิดพลาด

ต้องมี 10 หลัก เช่น 0812345678
ไม่กรอก = จัดส่งเร็วที่สุด
Labelวางเหนือช่องเสมอ Placeholder ใช้เป็นตัวอย่าง ไม่ใช้แทน label
Error timingแสดงตอน blur หรือ submit และหายทันทีเมื่อแก้ถูก
Error messageบอกว่าค่าที่ถูกต้องต้องเป็นอย่างไร ไม่ใช่แค่ “รูปแบบไม่ถูกต้อง”
Input typeใช้ email, tel, number, inputmode ให้เหมาะกับ keyboard บนมือถือ
Long formถ้าเกิน 8–10 ช่อง แบ่งเป็นขั้นและบอก progress
Defaultsเติมสิ่งที่รู้อยู่แล้วและอย่าล้างข้อมูลเมื่อ validation fail

06Modal, Drawer, หน้าใหม่ — Tabs vs Accordion

Controlใช้เมื่อหลีกเลี่ยงเมื่อ
Modalงานสั้น 1–3 ช่อง หรือยืนยัน action ทำลายForm ยาว เนื้อหาที่ต้องเทียบ หรือ mobile flow ซับซ้อน
DrawerMaster-detail หรือ filter ขั้นสูง โดยยังเห็น context เดิมตาราง/กราฟกว้าง
New Routeงานหลายขั้น มี URL แชร์/ย้อนกลับ และ form ยาวดูข้อมูลแวบเดียวแล้วกลับ
Popoverคำอธิบายสั้นหรือ action 2–4 อันข้อมูลสำคัญที่ต้องอ่าน โดยเฉพาะบน touch
Tabs2–6 กลุ่มระดับเดียวกัน ดูทีละกลุ่มและสลับไปมาForm ที่ต้องกรอกทุก tab หรือข้อมูลที่ควรเห็นพร้อมกัน
Accordionเนื้อหายาวหลายส่วนหรือ mobileสิ่งสำคัญที่ไม่ควรถูกซ่อน

Modal ที่ดี: focus ย้ายเข้าเมื่อเปิดและกลับที่เดิมเมื่อปิด, รองรับ Esc, และไม่ซ้อน modal บน modal

07Accessibility — ได้ UX ที่ดีขึ้นพร้อมกัน

Contrastข้อความทั่วไปอย่างน้อย 4.5:1 และตัวใหญ่ 3:1
ไม่ใช้สีอย่างเดียวError และสถานะต้องมีข้อความ/ไอคอนร่วมด้วย
Keyboardทุกสิ่งที่คลิกได้ต้อง Tab ไปถึง ใช้ Enter/Space ได้ และ focus ring เห็นชัด
LabelsInput มี label, icon button มี aria-label, image มี alt ที่เหมาะสม
Semantic HTMLใช้ button สำหรับ action และ a สำหรับ navigation ไม่ใช้ div onclick
Touch / Zoomเป้ากด ≥ 44 px และซูม 200% แล้ว layout ยังใช้งานได้
Motionเคารพ prefers-reduced-motion และหลีกเลี่ยง flashing

Checklist ก่อนส่งหน้าจอให้ทีม

สรุปใจความสำคัญ

UI ที่ดีเริ่มจากการถามว่า “ผู้ใช้ต้องตัดสินใจอะไร มีกี่ทางเลือก และการเปลี่ยนค่านี้มีผลเมื่อไร” เมื่อโจทย์ชัด การเลือก control, hierarchy ของปุ่ม, feedback และระดับการรบกวนผู้ใช้จะตามมาเอง พร้อมตรวจ accessibility เป็นส่วนหนึ่งของ UX ไม่ใช่งานเสริมภายหลัง
