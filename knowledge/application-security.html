01SQL Injection — เมื่อข้อมูลกลายเป็นคำสั่ง

ช่องโหว่เกิดจากเอาค่าของผู้ใช้ต่อเข้า SQL string โดยตรง ทำให้ฐานข้อมูลแยกไม่ออกว่าส่วนไหนคือ value และส่วนไหนคือ SQL syntax

ต่อ string
parameterized
// ❌ ไม่ควร
var sql = "SELECT * FROM Users WHERE Name = '" + name + "'";
var cmd = new SqlCommand(sql, conn);

// interpolation แล้วส่งเป็น string ก็ยังอันตราย
var sql2 = $"SELECT * FROM Users WHERE Name = '{name}'";
// ✅ SQL กับ value แยกจากกัน
var cmd = new SqlCommand(
    "SELECT * FROM Users WHERE Name = @name", conn);
cmd.Parameters.Add("@name", SqlDbType.NVarChar, 100).Value = name;

// Dapper
conn.Query<User>(
    "SELECT * FROM Users WHERE Name = @name", new { name });

จำง่าย: การป้องกันหลักคือ parameterized query ไม่ใช่การ escape quote หรือ blocklist อักขระ

02EF Core ปลอดภัยตรงไหน และยังพลาดได้ตรงไหน

LINQ และ API ที่ parameterize ให้จะปลอดภัยกว่า จุดเสี่ยงคือ Raw SQL ที่เอาค่าผู้ใช้ประกอบเป็น string ก่อนส่งเข้า EF

วิธีสถานะเหตุผล
Where(u => u.Name == name)ปลอดภัยEF สร้าง parameter ให้ value
FromSql($"... {name}")ปลอดภัยเมื่อใช้ API ที่รับ FormattableStringค่าถูกแยกเป็น parameter
FromSqlRaw($"... '{name}'")เสี่ยงinterpolation กลายเป็น string ก่อนถึง EF
ชื่อ column/table จาก userต้องระวังidentifier parameterize ไม่ได้ ต้อง whitelist
// ❌ ดูเหมือนสะดวกแต่เสี่ยง
var users = db.Users
    .FromSqlRaw($"SELECT * FROM Users WHERE Name = '{name}'")
    .ToList();
// ✅ value เป็น parameter
var users = db.Users
    .FromSql($"SELECT * FROM Users WHERE Name = {name}")
    .ToList();

var allowed = new[] { "Name", "CreatedAt" };
if (!allowed.Contains(sortBy)) sortBy = "CreatedAt";

Rule of thumb: เห็นคำว่า Raw ให้หยุดตรวจว่ามี user input อยู่ใน string หรือไม่

03XSS — เมื่อข้อมูลกลายเป็น HTML/JavaScript

Stored XSS เกิดเมื่อ attacker ฝาก script ไว้ในข้อมูล แล้วหน้าเว็บของผู้ใช้คนอื่นเอาข้อมูลนั้นไป render แบบ HTML โดยไม่ encode/sanitize

ผู้โจมตีกรอก comment ที่มี scriptข้อมูลถูกบันทึกลง DB ได้ตามปกติ
↓
ระบบอ่าน comment จาก DBDB ไม่ได้รู้ว่านี่คือโค้ดหรือข้อความ
↓
หน้าเว็บ render ด้วย innerHTML / Html.Rawbrowser จึงตีความเป็น executable HTML/JS
// ❌ Razor
@Html.Raw(comment.Body)

// ❌ JavaScript
el.innerHTML = comment.body;
// ✅ Razor encode ให้ตาม context
@comment.Body

// ✅ แสดงเป็น text
el.textContent = comment.body;

// rich text: sanitize ด้วย allowlist ที่เชื่อถือได้

Defense in depth: ใช้ output encoding ให้ถูก context, sanitize เมื่อจำเป็นต้องรองรับ HTML, ตั้ง CSP และใช้ cookie แบบ HttpOnly/Secure

04CSRF — ยืม session ของผู้ใช้ที่ login อยู่

ถ้า authentication อาศัย cookie เบราว์เซอร์อาจแนบ cookie ไปกับ request โดยอัตโนมัติ จึงต้องป้องกัน request ที่มาจากเว็บอื่น

Victim
login ระบบไว้ มี session cookie
Attacker
ล่อให้เปิดหน้าเว็บที่ยิง POST ไปยังระบบเป้าหมาย
Browser
ส่ง request พร้อม cookie ของระบบเป้าหมาย
Server
ถ้าไม่มี anti-forgery / SameSite ที่เหมาะสม อาจคิดว่าเป็นคำสั่งจริงจากผู้ใช้
[HttpPost, ValidateAntiForgeryToken]
public IActionResult Transfer(TransferDto dto) { ... }

builder.Services.ConfigureApplicationCookie(o => {
    o.Cookie.HttpOnly = true;
    o.Cookie.SecurePolicy = CookieSecurePolicy.Always;
    o.Cookie.SameSite = SameSiteMode.Strict;
});

แยกให้ชัด: API ที่ใช้ Bearer token ใน Authorization header และไม่ได้พึ่ง cookie สำหรับ auth มี threat model ด้าน CSRF ต่างจาก cookie-based session

05Authentication vs Authorization — login แล้วไม่ได้แปลว่าทำได้ทุกอย่าง

Authentication ตอบว่า “คุณคือใคร” ส่วน Authorization ตอบว่า “resource/action นี้คุณมีสิทธิ์หรือไม่” การตรวจแค่ [Authorize] จึงยังไม่พอสำหรับข้อมูลที่มีเจ้าของ

GET /orders/1001
User A
→
200 ของ A
GET /orders/1002
User A
→
200 ของ B ?

ถ้าเปลี่ยน id แล้วอ่านข้อมูลคนอื่นได้ นี่คือ Broken Access Control / IDOR

[Authorize]
[HttpGet("{id}")]
public Task<Order?> Get(int id)
    => db.Orders.FindAsync(id).AsTask();
[Authorize]
[HttpGet("{id}")]
public async Task<IActionResult> Get(int id)
{
    var userId = User.FindFirstValue(ClaimTypes.NameIdentifier);
    var order = await db.Orders
        .FirstOrDefaultAsync(x => x.Id == id && x.OwnerId == userId);
    return order is null ? NotFound() : Ok(order);
}

[Authorize(Policy = "CanRefund")]
public IActionResult Refund(int id) => ...;

กติกาสำคัญ: ownership/tenant/region/team ที่ใช้ตัดสิทธิ์ควรอยู่ใน query หรือ authorization policy ที่บังคับใช้จริง ไม่ใช่เชื่อ id/role ที่ client ส่งมา

DB password, API key และ signing key ไม่ควรอยู่ใน source code หรือไฟล์ config ที่ commit ขึ้น repo

07Password Storage — ต้องรั่วแล้วเอาไปใช้ต่อไม่ได้

Password ไม่ควรเก็บ plaintext และไม่ควรใช้ hash เร็วทั่วไปอย่าง MD5/SHA-256 โดยตรง ควรใช้ password hashing ที่มี salt และตั้ง cost ได้

// ASP.NET Core Identity / PasswordHasher
var hasher = new PasswordHasher<AppUser>();
user.PasswordHash = hasher.HashPassword(user, rawPassword);

var result = hasher.VerifyHashedPassword(
    user, user.PasswordHash, input);

เสริม: ใช้ lockout/rate limit ที่ login, ใช้ข้อความ error แบบไม่ช่วย enumerate user และ password reset ควรเป็น token ที่มีอายุ

08Input Validation — ตรวจที่ server เสมอ

Validation ไม่ได้แทน parameterized query หรือ output encoding แต่ช่วยจำกัด input domain และลดความผิดพลาดตั้งแต่ trust boundary

public record CreateOrderDto
{
    [Required, StringLength(200)]
    public string Note { get; init; } = "";

    [Range(1, 1000)]
    public int Quantity { get; init; }

    [RegularExpression("^[A-Z]{3}-[0-9]{4}$")]
    public string Sku { get; init; } = "";
}
Inputควรทำ
Uploadจำกัดขนาด ตรวจ content ตั้งชื่อใหม่ เก็บนอก public web root
ID / จำนวนใช้ type ที่ตรง เช่น int/Guid ไม่ปล่อย string อิสระเกินจำเป็น
Over-postingรับ DTO เฉพาะ field ที่อนุญาต ไม่ bind entity ตรง ๆ
Redirect URLvalidate destination กัน open redirect
Login / OTP / Searchใช้ rate limiting ตามความเสี่ยง

Allowlist มาก่อน blocklist: นิยามสิ่งที่อนุญาตให้ชัด ดีกว่าพยายามไล่ห้าม payload ที่เป็นไปได้ทั้งหมด

09Least Privilege — ถ้าชั้นแรกพลาด ต้องจำกัดความเสียหาย

Identity ของ app, DB user, service account และ cloud role ควรได้สิทธิ์เท่าที่งานจริงต้องใช้

-- application user ไม่ควรเป็น sa
CREATE LOGIN shop_app WITH PASSWORD = '...';
CREATE USER shop_app FOR LOGIN shop_app;

GRANT SELECT, INSERT, UPDATE
ON SCHEMA::dbo TO shop_app;

-- migration ใช้ identity แยกที่มีสิทธิ์แก้ schema
ชั้นหลักการ
Databaseแยก app identity กับ migration/admin identity
CloudManaged Identity / role เฉพาะ resource ที่ต้องใช้
Runtimeลดสิทธิ์ OS/container และ write access เมื่อทำได้
Errorproduction ไม่เผย stack trace/SQL ภายใน
Loggingไม่ log password, token, key หรือข้อมูลลับ; mask/redact ก่อน

Checklist ก่อนขึ้น Production

ใช้ทบทวน code review / release readiness และกดติ๊กเพื่อติดตามความครบถ้วนได้

สรุปใจความสำคัญ

แนวคิดหลักของ Application Security คือเริ่มจาก Trust Boundary ทุก input จาก client หรือระบบภายนอกถือว่าเชื่อไม่ได้ แล้วป้องกันตามจุดที่ข้อมูลถูกนำไปใช้: ถ้าเข้า SQL ต้อง parameterize, ถ้าออก HTML ต้อง encode/sanitize, ถ้าเข้าถึง resource ต้อง authorize ownership/permission ฝั่ง server และแม้ชั้นแรกพลาดก็ยังจำกัดผลกระทบด้วย secrets management, least privilege, safe logging และ security checks ใน CI/CD
