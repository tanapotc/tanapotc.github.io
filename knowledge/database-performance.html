04ชนิดของ Index ที่ควรรู้

Clustered

กำหนดลำดับของแถวจริง มีหนึ่งตัวต่อตาราง เหมาะกับ key ที่เล็กและเพิ่มแบบเป็นลำดับ

Nonclustered

โครงสร้างแยกจากตารางจริง มีได้หลายตัว ถ้าคอลัมน์ไม่ครบอาจเกิด Key Lookup

Composite

IX(CustomerId, OrderDate) ใช้หลัก leftmost prefix: คอลัมน์ด้านซ้ายสำคัญที่สุด

Covering / INCLUDE

พ่วงคอลัมน์ที่ต้องอ่านไว้ใน leaf เพื่อลด Key Lookup และจบ query ใน index

Unique

บังคับข้อมูลไม่ซ้ำและช่วย optimizer รู้ว่า seek จะคืนผลลัพธ์จำนวนจำกัด

Filtered

ทำ index เฉพาะ subset เช่น Pending jobs ที่เป็นส่วนน้อยของตารางแต่ถูก query บ่อย

05Sargable — มี Index แต่ทำไมยัง Scan?

ถ้าครอบคอลัมน์ด้วย function หรือแปลง type ก่อนเทียบ DB อาจใช้ลำดับใน index ไม่ได้

หลีกเลี่ยงเขียนแทน
YEAR(OrderDate)=2026OrderDate >= '2026-01-01' AND OrderDate < '2027-01-01'
LOWER(Email)=...normalize input ก่อน query หรือใช้ collation ที่เหมาะสม
LIKE '%keyword%'LIKE 'keyword%' หรือ Full-Text Search เมื่อโจทย์คือ contains จริง ๆ
Total * 1.07 > 1000ย้ายการคำนวณไปฝั่งค่าคงที่ เช่น Total > 1000 / 1.07
varchar column เทียบ nvarchar parameterกำหนด type/Unicode mapping ให้ตรง ลด implicit conversion

EF Core: ใช้ ToQueryString() เช็ก SQL จริง แล้วมองหา DATEPART, LOWER, CONVERT หรือ LIKE N'%...'

// Projection มักเหมาะกับ read-only API
var rows = await db.Orders
    .Where(o => o.Status == "Pending")
    .Select(o => new {
        o.Id,
        o.Total,
        CustomerName = o.Customer.Name
    })
    .AsNoTracking()
    .ToListAsync();

// ถ้าต้องการ entity graph
.Include(o => o.Customer)

// หลาย collection จน JOIN ระเบิด
.AsSplitQuery()

07Pagination — OFFSET หน้าลึกยิ่งแพง

OFFSET หน้าลึก

อ่าน 100,020 แถว → ใช้ 20

Keyset / Cursor

seek จาก lastSeenId → อ่านเฉพาะแถวถัดไป

// OFFSET
.OrderByDescending(o => o.Id)
.Skip((pageNo - 1) * 20)
.Take(20)

// Keyset
.Where(o => o.Id < lastSeenId)
.OrderByDescending(o => o.Id)
.Take(20)

Keyset เหมาะกับ infinite scroll และ API ที่ไล่อ่านต่อเนื่อง ส่วน OFFSET ยังสะดวกเมื่อจำเป็นต้องกระโดดไปหน้าที่ N

08Quick Wins ใน EF Core / SQL Server

ทำอะไรเหตุผล
Select เฉพาะคอลัมน์ลด network, materialization และเปิดโอกาสให้ covering index
AsNoTracking()ลด change-tracking overhead สำหรับ read-only query
Bulk update/deleteลด round-trip และการ materialize entity จำนวนมาก
Async ตลอดสายไม่ได้ทำให้ SQL เร็วขึ้น แต่ไม่ block request thread ระหว่างรอ I/O
Cache reference dataลด query ซ้ำกับข้อมูลที่เปลี่ยนน้อย
Connection poolingใช้ connection ซ้ำแทนการสร้างใหม่ทุก request
Statistics / Query Storeช่วย optimizer และช่วยหาการเปลี่ยน plan ที่ทำให้ performance แย่ลง

Checklist เมื่อเจอ Query ช้า

สรุปใจความสำคัญ

แนวทางในการวิเคราะห์ query ช้าควรเริ่มจากการวัดก่อนว่า bottleneck อยู่ที่ DB จริงหรือไม่ จากนั้นดู SQL และ Actual Execution Plan เพื่อหา Scan, Lookup, cardinality mismatch หรือ query pattern ที่ผิด แล้วค่อยแก้ด้วย index, projection, query rewrite, ลด N+1 หรือเปลี่ยน pagination สุดท้ายต้องวัด logical reads และเวลาอีกครั้งเพื่อยืนยันว่าแก้ถูกจุด
