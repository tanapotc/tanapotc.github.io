01Temperature และ top_p

temperature เปลี่ยนความแหลมของ distribution ส่วน top_p ตัดหางของ token ที่มีความน่าจะเป็นต่ำ ลองเลื่อนค่าเพื่อเห็นภาพผลของ sampling

temperatureต่ำ = token เดิมเด่นขึ้น, สูง = distribution แบนขึ้นและสุ่มมากขึ้น ไม่ได้ทำให้โมเดล “ฉลาดขึ้น”
top_pเรียง token ตาม probability แล้วเก็บเฉพาะกลุ่มที่ cumulative probability ถึง p
ปรับอย่างไรโดยทั่วไปควรปรับ temperature หรือ top_p ตัวหลักตัวเดียว เพื่ออธิบายผลได้ง่าย
Tool / JSONงาน extract, classify, tool calling หรือ output ที่ต้อง parse ควรลดความสุ่มและใช้ structured output

02ค่าอื่นตอนสร้างคำตอบ

Parameterผลกระทบข้อควรระวัง
max_tokensกำหนดเพดาน output และช่วยคุม costต่ำเกินไปอาจตัดคำตอบหรือ JSON กลางทาง
structured outputบังคับ schema เมื่อต้อง parse ผลต่อschema ซับซ้อนเกินไปทำให้คุณภาพลดลงได้
reasoning effortให้โมเดลใช้การคิดมากขึ้นในงานวางแผน/code/การตัดสินใจหลายขั้นเพิ่ม latency และ cost จึงควรตั้งราย node
frequency / presence penaltyลดการวนคำหรือคำซ้ำสูงเกินไปอาจเลี่ยงคำเฉพาะที่จำเป็น
seedช่วยลด noise ใน eval แบบ best-effortไม่ได้รับประกัน deterministic 100%
tool_choiceauto / none / required / specific toolใช้ required เมื่อรู้ว่าขั้นนั้นต้องเรียก tool จริง
parallel tool callsลดจำนวนรอบเมื่อเรียก read-only tools ที่ไม่ขึ้นต่อกันปิดเมื่อมี side effect หรือลำดับสำคัญ

03Cosine Similarity และ Retrieval Parameters

Similarity Metric

Cosineวัดมุมของ vector และเป็น default ที่ใช้บ่อยกับ text embedding
Dot Productรวมทั้งทิศทางและความยาว; ถ้า vector normalize แล้วผลสัมพันธ์กับ cosine
Euclideanวัดระยะปลาย vector เหมาะเมื่อ magnitude มีความหมาย

คะแนน cosine ไม่ใช่เปอร์เซ็นต์ความเกี่ยวข้อง threshold ต้องหาโดยดู distribution จากข้อมูลจริงของระบบ

ลูกบิดเริ่มคิดจากอะไร
top_kน้อยเกินไป recall ต่ำ มากเกินไป context มีของไม่เกี่ยว
score thresholdหา threshold จาก eval set ไม่ใช่ตั้งตัวเลขลอย ๆ
chunk sizeตัดตามโครงเอกสารและรักษาบริบท
overlapช่วยไม่ให้ข้อมูลที่ข้าม boundary หาย แต่ overlap มากไปเกิด chunk ซ้ำ
hybrid weightสมดุล semantic vector กับ keyword/BM25 โดยเฉพาะรหัสหรือชื่อเฉพาะ
rerankดึง candidate มากก่อน แล้วให้ reranker เลือกชิ้นที่ตรงจริงเข้า prompt
HNSWแลก speed กับ recall ผ่าน search/index parameters

04Prompt — ลูกบิดที่ใหญ่ที่สุด

โทน บทบาท ความยาว รูปแบบ และกติกาเป็นงานของ prompt ไม่ใช่ temperature

## บทบาท
คุณเป็นผู้ช่วยฝ่ายจัดซื้อของบริษัท X

## งาน
ดูสินค้าที่สต็อกใกล้หมด หา supplier และเตรียม PO

## กติกา
- ห้ามสร้าง PO ก่อนรู้ supplier
- ถ้ายอดเกินวงเงินต้องขออนุมัติ
- ถ้าข้อมูลไม่พอให้ถามกลับ

## รูปแบบผลลัพธ์
สรุปการตัดสินใจและ action ที่ทำไป
Few-shotใช้ตัวอย่างจริงเพื่อสอน style และ boundary ของ output
Tool descriptionคำอธิบาย tool เป็น prompt สำคัญ ต้องบอกใช้เมื่อไรและ parameter หมายถึงอะไร
Output formatถ้าต้อง parse ให้ใช้ schema; ถ้าเป็นคนอ่านให้ระบุความยาวและโครงให้ชัด

05ลูกบิดของ Agent Loop

max_turns / max_costเป็น hard limit กัน loop และค่าใช้จ่าย runaway
tool timeoutจำกัดเวลารอแต่ละ tool และส่งสถานะกลับให้ orchestrator ตัดสินต่อ
retryretry LLM/network error แบบเหมาะสม แต่ tool ที่มี side effect ต้องพึ่ง idempotency มากกว่าการ retry ตรง ๆ
context budgetเหลือพื้นที่ให้ output และรอบถัดไป; history/tool result เก่าควรถูกสรุปหรือย่อ
model per stepใช้โมเดลเร็ว/ประหยัดกับ classify/route และใช้โมเดลเก่งขึ้นเฉพาะ step ที่ต้อง reasoning
tool_choice per stepบาง node ควรบังคับ retrieval/tool บาง node ควรปิด tool เพื่อสรุปคำตอบ
approval gateเริ่มจาก approval สำหรับ write/pay/send แล้วค่อยผ่อนเมื่อมี evidence จาก log/evals
early stopหยุดเมื่อสำเร็จหรือเมื่อพบ loop pattern เช่น tool call ซ้ำเดิม

06Preset ตามชนิดงาน

งานแนวทางเริ่มต้น
Classify / Routeความสุ่มต่ำ, output สั้น, enum/schema, reasoning ต่ำ
Extractstructured output, ค่าที่ไม่มีให้ null แทนการเดา
RAG Q&Ageneration ค่อนข้างนิ่ง + hybrid retrieval + rerank + ยอมรับคำตอบ “ไม่พบ”
Agent Tool Callingความสุ่มต่ำ, max turns, tools ตาม node และ parallel เฉพาะ read-only
Chat / Writingเพิ่มความหลากหลายได้ตามงาน แต่ tone/length คุมด้วย prompt
Codereasoning และการรัน test สำคัญกว่าการเพิ่ม temperature

07ปรับอย่างเป็นระบบ

ขั้นทำอะไร
1สร้าง eval set จากเคสจริงก่อน
2รัน baseline และดูค่าเฉลี่ย/ความแปรปรวน
3เปลี่ยนทีละ parameter หรือ prompt ทีละจุด
4เปิด trace ดูว่าพังที่ retrieval, tool selection, loop หรือ generation
5เก็บค่าที่ผ่าน eval ลง config ที่ version ได้
อาการสงสัยก่อน
ตอบไม่คงที่prompt คลุมเครือหรือ sampling สูง
“ไม่พบ” ทั้งที่มีเอกสารretrieval recall, top_k, threshold, chunking
เลือก tool ผิดtool description, จำนวน tools, tool_choice
วนไม่จบtool result, early stop, graph/loop design
JSON พังstructured output, max tokens, sampling
ช้า/แพงreasoning effort, model per step, context/history
