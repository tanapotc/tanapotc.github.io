01Unit Test อยู่ตรงไหนในภาพรวม

“unit” คือหน่วยของพฤติกรรมที่ทดสอบได้โดยไม่ต้องมี database, network, file หรือเวลาจริง ยิ่งอยู่ฐานล่างยิ่งเร็วและควรมีจำนวนมาก

End-to-endHTTP จริงผ่านทุกชั้นถึง DBช้าและแพง จึงเก็บไว้เฉพาะ flow สำคัญ
IntegrationRepository + DB จริง / API ผ่าน WebApplicationFactoryตรวจ SQL, mapping และ DI
UnitDomain, value object, handler + fake, pure functionเร็ว ไม่มี I/O และรันได้จำนวนมาก
เป้าหมายให้กล้าแก้โค้ด เพราะ regression ถูกจับได้เร็ว
Coverageตัวเลข coverage เป็นเพียงสัญญาณ สิ่งสำคัญคือกติกาธุรกิจและ error path
เริ่มจากDomain → Application → ส่วนที่แตะระบบจริงใช้ Integration
ไม่จำเป็นต้องเทสproperty ธรรมดา, mapping ตรง ๆ, behavior ของ framework หรือสิ่งที่ compiler บังคับแล้ว
Unit = 1 class?ไม่จำเป็น หน่วยที่เทสคือ “พฤติกรรม” และอาจประกอบด้วยหลาย object ตราบใดที่ไม่มี I/O

02Arrange – Act – Assert

เทสหนึ่งตัวแบ่งเป็น 3 ช่วงให้เห็นชัด ถ้าช่วงใดยาวผิดปกติ มักเป็นสัญญาณว่าการออกแบบ object หรือ test setup ซับซ้อนเกินไป

Arrange — เตรียมสร้าง object และข้อมูลตั้งต้นให้ตรง scenario
Act — ทำเรียกพฤติกรรมที่กำลังทดสอบหนึ่งครั้ง
Assert — ตรวจตรวจผลหรือ state ที่เป็นสัญญาของ scenario นั้น
// Shop.Domain.Tests/Orders/OrderTests.cs
[Fact]
public void Ship_WhenPending_ChangesStatusToShipped()
{
    // Arrange
    var order = OrderBuilder.Pending().WithLines(2).Build();

    // Act
    order.Ship();

    // Assert
    order.Status.Should().Be(OrderStatus.Shipped);
}

[Fact]
public void Ship_WhenAlreadyShipped_Throws()
{
    var order = OrderBuilder.Shipped().Build();
    var act = () => order.Ship();
    act.Should().Throw();
}
Arrangeใช้ builder/factory เพื่อซ่อน default ที่ไม่เกี่ยวกับ scenario
Actควรเป็น 1 action หลัก ถ้ามีหลาย action อาจกำลังเทสหลาย behavior
Assertหลาย assertion ได้เมื่อทั้งหมดอธิบายผลของเรื่องเดียวกัน
หลีกเลี่ยงif, loop, try/catch ใน test; หลาย input ใช้ [Theory]

Given / When / Then คือแนวคิดเดียวกันในภาษา BDD: Given = Arrange, When = Act, Then = Assert

[Theory]
[InlineData(99)]
[InlineData(50_001)]
[InlineData(0)]
public void Create_WithTotalOutsideRange_Throws(decimal total)
{
    var act = () => Order.Create(1, LinesTotaling(total));
    act.Should().Throw();
}

[Theory]
[InlineData(100)]
[InlineData(1_500)]
[InlineData(50_000)]
public void Create_WithTotalInRange_Succeeds(decimal total)
{
    var order = Order.Create(1, LinesTotaling(total));
    order.Total.Should().Be(total);
}

05Test Doubles — ตัวแทนของ Dependency

Unit test ไม่ควรเรียก DB, network หรือเวลาจริง จึงใช้ dependency ที่ควบคุมได้แทน โดยชื่อเรียกขึ้นกับพฤติกรรมของตัวแทนนั้น

Stub

คืนค่าที่กำหนดไว้ ใช้กับ dependency ที่ให้ข้อมูล

clock.UtcNow → วันที่คงที่, repo.Get → object ที่เตรียมไว้

Mock

ตรวจว่า interaction สำคัญถูกเรียกหรือไม่

emailSender.Send ถูกเรียก 1 ครั้งด้วย recipient ที่ถูกต้อง

Fake

implementation จริงแบบง่ายที่ไม่มี I/O

InMemoryOrderRepository เก็บข้อมูลใน List<Order>
public class FakeOrderRepository : IOrderRepository
{
    public List Orders { get; } = [];

    public Task GetWithLinesAsync(int id, CancellationToken ct)
        => Task.FromResult(Orders.FirstOrDefault(o => o.Id == id));

    public void Add(Order order) => Orders.Add(order);
}

public class FakeUnitOfWork : IUnitOfWork
{
    public int SaveCount { get; private set; }
    public Task SaveChangesAsync(CancellationToken ct)
    {
        SaveCount++;
        return Task.FromResult(1);
    }
}
[Fact]
public async Task Handle_WhenPlaced_SendsConfirmationEmail()
{
    var repo = new FakeOrderRepository();
    var uow = new FakeUnitOfWork();
    var email = Substitute.For();
    var clock = Substitute.For();
    clock.UtcNow.Returns(new DateTime(2026, 9, 11));

    var handler = new PlaceOrderHandler(repo, uow, email, clock);
    await handler.Handle(command, default);

    repo.Orders.Should().ContainSingle();
    uow.SaveCount.Should().Be(1);
    await email.Received(1).SendAsync(
        Arg.Any(), Arg.Any(), Arg.Any());
}

หลักคิด: Fake เหมาะกับ repository ที่มี behavior ให้ใช้ซ้ำ, Mock เหมาะกับ side effect ที่ส่งออกไป เช่น email/event/payment และ entity/value object ของเราเองควรใช้ของจริง

07Test Smells — เทสที่เขียนยากกำลังบอกอะไร

กลิ่นสาเหตุที่มักเป็นแนวทาง
Arrange 20 บรรทัดobject graph หรือ dependency เยอะใช้ Builder และพิจารณาแยก class
ต้อง mock 6 ตัวclass ทำหลายหน้าที่กลับไปดู SRP
refactor แล้ว test พังทั้งที่ behavior เดิมเทส implementation detailassert ผลลัพธ์/state สุดท้าย
DateTime.Now / Guid / Randomผลไม่ deterministicinject IClock / IIdGenerator แล้ว stub
test ต้องรันตามลำดับแชร์ mutable/static stateทุก test สร้าง state ของตัวเอง
เปิด private เป็น public เพื่อเทสbehavior อาจควรเป็น object แยกเทสผ่าน public API หรือ extract class
assert แค่ไม่ throwยังไม่ชัดว่า behavior ที่ต้องการคืออะไรถามว่าถ้า logic ผิด ผลลัพธ์ต่างตรงไหน
คำนวณ expected ด้วย logic เดียวกับ productiontest อาจผิดเหมือน productionใช้ literal ที่คำนวณแยกจาก implementation

coverlet + ReportGeneratorดูส่วนที่ยังไม่มี coverage โดยไม่ใช้ตัวเลข coverage เป็นเป้าหมายหลัก

Checklist ก่อน Commit Test

สรุปใจความสำคัญ

Unit test ที่ดีคือข้อกำหนดที่รันได้: เลือกทดสอบ behavior และ business rule มากกว่า implementation detail, ออกแบบ case จาก partition + boundary + error path, แยก I/O ออกด้วย fake/stub/mock ตามหน้าที่ และใช้ integration test เมื่อต้องยืนยัน behavior ของฐานข้อมูลหรือ HTTP จริง ถ้า test เขียนยาก ให้ใช้ความยากนั้นเป็นสัญญาณย้อนกลับไปตรวจ design ของ production code
