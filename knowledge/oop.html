01Class กับ Object

Class คือ blueprint ส่วน Object คือ instance จริงที่สร้างจาก blueprint นั้น หนึ่ง class สร้าง object ได้หลายตัวและแต่ละตัวมี state ของตัวเอง

public class Product
{
    public string Name { get; }
    public decimal Price { get; }
    public int Stock { get; private set; }

    public Product(string name, decimal price, int stock)
        => (Name, Price, Stock) = (name, price, stock);

    public bool IsAvailable() => Stock > 0;
}

var laptop = new Product("ThinkPad", 32000m, 4);
var mouse  = new Product("MX Master", 3200m, 0);

จำสั้น ๆ: Class บอกว่า “ของชนิดนี้มีอะไรและทำอะไรได้” ส่วน Object คือของชิ้นหนึ่งที่มีค่าจริงอยู่ข้างใน

02Encapsulation — ห่อข้อมูลไว้ เปิดแค่ประตู

state ภายในไม่ควรถูกแก้จากข้างนอกแบบอิสระ แต่ควรเปลี่ยนผ่าน method/property ที่ตรวจ business rule ได้

public class BankAccount
{
    private decimal _balance;
    public decimal Balance => _balance;

    public void Deposit(decimal amount)
    {
        if (amount <= 0) throw new ArgumentException();
        _balance += amount;
    }

    public void Withdraw(decimal amount)
    {
        if (amount > _balance)
            throw new InvalidOperationException("ยอดไม่พอ");
        _balance -= amount;
    }
}

จำสั้น ๆ: ให้ private เป็นค่าเริ่มต้น แล้วเปิด public เท่าที่ผู้ใช้งาน object จำเป็นต้องใช้จริง

03Inheritance — ต่อยอดจากของที่มีอยู่

ใช้เมื่อความสัมพันธ์พูดได้ว่า “ลูกเป็นชนิดหนึ่งของแม่” หรือ is-a และลูกต้องใช้ contract/behavior ร่วมจาก base class

public abstract class Payment
{
    public decimal Amount { get; }
    public abstract PaymentResult Process();
    public string Receipt() => $"{Amount:N2} บาท";
}

public class PromptPayPayment : Payment
{
    public override PaymentResult Process()
        => PromptPayGateway.Verify(...);
}

ระวัง: Inheritance ผูก class ลูกกับ base class ค่อนข้างแน่น ถ้าความสัมพันธ์จริงคือ “มี” (has-a) ให้พิจารณา Composition แทน

04Polymorphism — คำสั่งเดียว ผลต่างกันตามตัวจริง

ฝั่งเรียกใช้อ้างอิงผ่าน base type/interface เดียวกัน แต่ runtime เลือก implementation ของ object จริงให้เอง

public class CheckoutService
{
    public void Checkout(Order order, Payment payment)
    {
        var result = payment.Process();
        if (result.Success)
            order.MarkPaid(payment.Receipt());
    }
}

// เพิ่ม payment แบบใหม่ได้โดยเพิ่ม class ใหม่
// CheckoutService ไม่ต้องเพิ่ม switch ตามชนิด

จำสั้น ๆ: เขียนโค้ดคุยกับ abstraction แล้วปล่อยให้ implementation จริงตัดสินใจ behavior ของตัวเอง

05Abstraction — โชว์แค่สิ่งที่ผู้ใช้ต้องรู้

ซ่อนรายละเอียดที่ไม่เกี่ยวกับผู้ใช้ component แล้วเปิดเพียง contract ระดับสูง เพื่อให้โค้ดฝั่งเรียกไม่ผูกกับ implementation

สิ่งที่ Checkout ต้องเห็น
IPaymentGateway.Charge(amount)
implementation boundary
HTTP client / authentication / retry / provider payload / signature / logging / mapping response
public interface IPaymentGateway
{
    Task ChargeAsync(decimal amount);
}

public class CheckoutService
{
    private readonly IPaymentGateway _gateway;

    public CheckoutService(IPaymentGateway gateway)
        => _gateway = gateway;
}

Abstraction ไม่ใช่แค่ interface: เป้าหมายคือทำให้ caller สนใจ “ต้องการอะไร” มากกว่า “ข้างในทำอย่างไร”

06Interface กับ Abstract class ใช้อันไหน

Interface — สัญญา

IPaymentGateway
ChargeAsync()
RefundAsync()

ใช้เมื่ออยากบอกว่า object “ทำอะไรได้” และต้องการให้ implementation หลายแบบแทนกันได้ โดยไม่ต้องแชร์ state ของแม่

Abstract class — แม่ครึ่งสำเร็จรูป

Payment
shared state: Amount
abstract Process()
shared Receipt()

ใช้เมื่อ derived class มีแกนร่วมจริง ทั้ง state และ behavior และความสัมพันธ์ is-a ชัดเจน

แนวคิดใช้งาน: Interface เหมาะกับ contract/DI และความยืดหยุ่น ส่วน Abstract class เหมาะกับ base behavior ที่ลูกต้องแชร์จริง ๆ

07Composition — “มี” ดีกว่า “เป็น” ในหลายกรณี

แทนที่จะสร้าง inheritance tree เพื่อรวม behavior หลายแบบ ให้ object ถือ dependency ที่ต้องใช้แล้วประกอบ behavior จากชิ้นส่วนเหล่านั้น

ผูกแน่นด้วย inheritance

BaseOrder
 └─ DiscountOrder
     └─ AuditedDiscountOrder
         └─ LoggedAuditedDiscountOrder

behavior หลายมิติถูกบังคับให้อยู่ในต้นไม้เดียว เปลี่ยนลำดับหรือ mix ใหม่ยาก

ประกอบจาก dependency

เปลี่ยนแต่ละ behavior ผ่าน DI ได้ง่าย ทดสอบแยกได้ และไม่ต้องเพิ่มชั้น inheritance

หลักคิด: ถ้าความสัมพันธ์คือ has-a ให้ Composition ก่อน ถ้าเป็น is-a จริงและต้องแชร์ state/behavior จึงค่อยใช้ Inheritance

OOP ไม่ได้แปลว่าแค่สร้าง class เยอะ ๆ แต่คือการออกแบบ boundary ของ object ให้ state กับ behavior ที่เกี่ยวกันอยู่ด้วยกัน ซ่อน implementation ที่ไม่ควรให้ภายนอกแตะ และเปิด contract ที่ชัดเจน จากนั้นใช้ polymorphism และ composition เพื่อลด coupling และทำให้ระบบขยายหรือทดสอบได้ง่ายขึ้น
